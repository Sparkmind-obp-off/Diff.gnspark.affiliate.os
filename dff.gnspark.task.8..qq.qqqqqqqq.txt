6. OPPORTUNITY LIFECYCLE

Define a minimal deterministic lifecycle based on the actual existing Opportunity model.

Do NOT invent a large CRM/workflow system.

The initial lifecycle should be intentionally small.

Use the following state model unless the existing repository contains a clearly established compatible model that must be preserved:

draft
→ active
→ completed

And:

draft
→ archived

active
→ archived

→ archived

The system MUST NOT silently mutate state.

Do NOT add speculative states such as:

approved

unless the existing repository/domain contract explicitly requires them.

If the existing domain already contains a lifecycle vocabulary, reconcile it carefully rather than duplicating it.

7. TRANSITION RULES

Create one deterministic transition policy.

Example conceptual contract:

canTransition(from, to)

and/or:

transitionOpportunity(...)

The policy MUST be centralized.

Do NOT place lifecycle rules directly inside route handlers.

Routes should call the application/service layer.

Invalid transition must return a safe domain/application error.

The transition operation must be deterministic.

No client-controlled bypass.

8. AUTHORIZATION

Task 08 MUST consume that existing boundary.

Do NOT implement a second authorization system.

Create Opportunity

Update lifecycle

requires an appropriate existing permission.

If the existing permission vocabulary does not contain a dedicated lifecycle/update permission, use the smallest compatible existing permission rather than inventing an uncontrolled permission.

Do NOT expand the permission catalogue unnecessarily.

Authorization must happen BEFORE mutation.

The server derives:

account
workspace
membership
role
permission

from authenticated server-side context.

Never trust:

client-provided account_id
client-provided workspace_id
client-provided role
client-provided permission

9. TENANT ISOLATION

Tenant isolation remains mandatory.

Every Opportunity operation MUST remain scoped to:

workspace_id

A user in Workspace A MUST NOT be able to:

read Workspace B opportunities
update Workspace B opportunities
change Workspace B opportunity state
archive Workspace B opportunities
infer sensitive information from cross-tenant IDs

Repository methods MUST preserve workspace scoping.

Preferred conceptual shape:

getOpportunity(workspaceId, opportunityId)

listOpportunities(workspaceId, ...)

updateOpportunity(workspaceId, opportunityId, ...)

transitionOpportunity(workspaceId, opportunityId, ...)

Never:

getOpportunity(opportunityId)

if that allows tenant context to be omitted.
